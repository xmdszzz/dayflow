Task Routing — 每条消息先路由到 Task Node

匹配度判断 → 路由到已有 Node / 新建 Node

🔀 决策流程图

每条 user message 的处理链路
👤 用户输入："把会议改到下午3点"
↓
Step 1: 构建候选池
收集所有 status=pending 且未过期的 Task Node
每个 Node 带上它的 chat_messages 摘要
作为候选池发给 LLM
↓
Step 2: LLM 匹配判断
传入候选池 + 用户输入
LLM 调用 route_message
返回最匹配的 task_id
或返回 null（无匹配）
↓
✅ 命中已有 task
LLM 返回 task_id = "t-001"
→ 消息挂载到 t-001
→ LLM 接着判断意图 update/delete/query
🆕 无匹配
LLM 返回 task_id = null
→ LLM 调用 add_task 创建新 Node
→ 消息挂载到新 task_id

🧠 LLM 路由 Prompt (核心)

Route Function 定义
route_message {
  task_id: string | null,
  confidence: 0-1,
  reason: string
}

// 匹配规则（LLM 自主判断）：
// 1. 语义相似度 — 事件描述、人物、地点是否相关
// 2. 指代消解 — "会议"指哪个会议？找最近的
// 3. 时间邻近 — 同一时段的任务优先级更高
// 4. 显式引用 — "把刚才那个..."指最近一轮对话的task
System Prompt 片段
你是一个日程助手。收到用户消息后，
第一步调用 route_message 判断属于哪
个已有任务，或是否需要新建。

候选任务池：
1. [t-001] 6/5 10:00 项目评审会 @3号会议室
   最近消息："改到10点吧"
2. [t-003] 6/4 20:00 健身·练腿
   最近消息："晚上8点去健身房练腿"

用户输入："把会议改到下午3点"

分析：
- "会议"大概率指 t-001 项目评审会
- t-003 是健身，不相关
- confidence 高，因为语义匹配明确

→ route_message(t-001, 0.95, "会议指项目评审会")

⚡ 优化：两段式调用 vs 一段式

方案 流程 延迟 判断
两段式 ① route_message → 拿到 task_id
② 带 task_id 再调 LLM 执行具体操作 		2× API 调用 ~1.5s 逻辑清晰，可独立调试
但用户感知慢
一段式 ⭐ 一次调用，LLM 先判断归属再执行操作
tools: [route_message, add_task, update_task, ...]
LLM 自主决定调用顺序 		1× API 调用 ~0.8s 快，LLM 自己规划调用顺序
DeepSeek function calling 支持多 tool 串联
推荐

📋 完整 Tools 清单

发给 DeepSeek 的 tools 数组
Tool 触发时机 参数
route_message 每次调用，第一步 task_id: string|null, confidence: number, reason: string
add_task route 返回 null 或显式新建 date, time, place, person, event
update_task 修改已有任务的字段 task_id, date?, time?, place?, person?, event?
delete_task 取消/删除任务 task_id
query_tasks 查询某天/某周的任务 date?, date_range?, person?, keyword?

🔄 端到端流程

async function handleUserMessage(userInput: string) {

  // 1. 构建候选池
  const candidates = db.getActiveTasksWithSummary();
  // [{id, date, time, place, person, event, recentMsgs: "改到10点吧"}]

  // 2. 构建上下文（只含活跃 task 的消息）
  const messages = buildContext(userInput, candidates);

  // 3. 一次 LLM 调用，tools 全传进去
  const response = await deepseek.chat({
    model: 'deepseek-chat',
    messages,
    tools: [route_message, add_task, update_task, delete_task, query_tasks],
    tool_choice: 'auto',
  });

  // 4. 按 LLM 返回的 tool_calls 依次执行
  for (const call of response.tool_calls) {
    switch (call.name) {
      case 'route_message':
        targetTaskId = call.args.task_id;  // null → 新建
      case 'add_task':
        targetTaskId = db.createTask(call.args);
      case 'update_task':
        db.updateTask(call.args.task_id, call.args);
      case 'delete_task':
        db.deleteTask(call.args.task_id);  // → 触發折叠
      case 'query_tasks':
        result = db.queryTasks(call.args);
    }
  }

  // 5. 消息挂载到 task
  db.saveMessage({ task_id: targetTaskId, role: 'user', content: userInput });
  db.saveMessage({ task_id: targetTaskId, role: 'assistant', content: responseText });

  // 6. 如果 task 状态变为 done → 立即触发折叠
  if (task.status === 'done') {
    compressTaskMessages(targetTaskId);  // 压缩 → memory
  }
}
